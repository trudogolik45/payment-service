# Списание без блокировки строки Платежа

Списание у эмулятора идёт 2–5 с, у настоящего шлюза — сколько угодно. Раньше
каждый шаг Обработки шёл под `SELECT … FOR UPDATE`, и всё это время транзакция
держала строку Платежа и соединение из пула consumer'а. Теперь Обработка коротко
читает Платёж, вызывает шлюз вне транзакции (ключ к шлюзу — id Платежа) и пишет
статус и дату обработки по условию «Платёж ещё ожидает». Если запись затронула
0 строк, параллельная доставка успела раньше: Платёж перечитывается, и Обработка
продолжает с тем, что в БД. Уведомление тоже отправляется без блокировки, отметка
о доставке пишется по условию «ещё не доставлено».

## Considered Options

- **Блокировка строки на всё Списание** (было). Две доставки идут строго по
  очереди, но транзакция и соединение простаивают, пока отвечает шлюз или
  webhook. Пул consumer'а приходится держать не меньше prefetch.
- **Статус «в обработке» в БД**. Вторая доставка видит его и не идёт в шлюз, но
  статуса нет в ТЗ (ожидает / успешен / отклонён), нужна миграция, а при падении
  consumer'а Платёж застревает в «в обработке», и его надо кому-то возвращать.
- **Запись по условию без блокировки** (выбрано). Статусы из ТЗ не меняются,
  миграции нет. От двойного списания защищает ключ к шлюзу, от двух разных
  результатов в БД — условие в `UPDATE`.

## Consequences

- Уведомление — «как минимум один раз»: при двух одновременных доставках одного
  события оно может уйти дважды. Получатель отсекает дубли по id Платежа.
- Эмулятор шлюза помнит ключи только в пределах процесса, поэтому два consumer'а
  могут «списать» дважды; в БД остаётся один результат. Настоящий шлюз
  идемпотентен глобально, поэтому эмулятор не трогаем.
- Размер пула соединений consumer'а оставлен равным prefetch.
